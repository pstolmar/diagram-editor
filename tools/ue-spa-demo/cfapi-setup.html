CF OpenAPI & Headless Delivery

When you don't have a Publish instance — or don't want one

The two-page guide covers the standard setup: GraphQL persisted queries against a Publish endpoint. This page covers the differences when you're using the newer Content Fragments OpenAPI, when you're working Author-only, or when you want to query fragments without a traditional Publish/replication pipeline.

1 — Which approach is right for your situation

AEM offers several ways to deliver Content Fragment data to a frontend. The right one depends on whether you have a Publish instance, who your users are, and whether they need to authenticate.

GraphQL Persisted Queries Part 1 of this guide

  • Read-only, public-facing delivery
  • No authentication required from the browser
  • Responses cached at CDN — fast globally
  • Requires a Publish instance with content replicated to it
  • Queries defined and managed in AEM's GraphiQL
  • Best for: public SPAs, marketing sites, storefronts

CF OpenAPI (REST) this page

  • Read and write — can create, update, delete fragments
  • Requires an OAuth access token on every request
  • Can target Author directly — no Publish replication needed
  • Not safe for public-facing SPAs (token would be exposed)
  • No pre-defined query layer — filter by model, path, or tag
  • Best for: backend services, preview tools, editorial automation, server-side rendering

AEM Assets HTTP API

  • Older REST API; returns CF data as jcr:content JSON
  • Still works, but CF OpenAPI is the recommended replacement
  • Useful if you're on an AEM version that predates CF OpenAPI

Edge Delivery / Document-based

  • Content lives in SharePoint or Google Drive instead of AEM DAM
  • No Content Fragments, no GraphQL — completely different model
  • Not relevant if you're building CF-driven experiences

The short version: if your app is public-facing and you have a Publish instance, use GraphQL. If you need server-side access, preview without publishing, or write access, use CF OpenAPI.

2 — Content Fragments OpenAPI

The CF OpenAPI was introduced in AEM Cloud Service as a modern, standards-based alternative to the GraphQL layer. It exposes fragments as REST resources with a Swagger/OpenAPI spec you can import directly into Postman or any API client.

Base URL

# Can target Author (for preview/draft) or Publish (for live content)
https://author-p{prog}-e{env}.adobeaemcloud.com/adobe/sites/cf/fragments
https://publish-p{prog}-e{env}.adobeaemcloud.com/adobe/sites/cf/fragments

Authentication

Every CF OpenAPI request requires a bearer token issued by Adobe IMS. There are two token types depending on where your code runs:

Token typeWhere to use itHow to get it
Service credentials (JWT → access token) Server-side only — Node.js, Cloud Functions, CI scripts AEM → Tools → Security → Adobe IMS Configurations → create integration, download JSON
User access token When the caller is an authenticated Adobe user IMS OAuth flow; token from aio auth token or Adobe IMS APIs
Never expose credentials in a public-facing SPA

CF OpenAPI tokens grant write access to your content. If you put a service credential or client secret in client-side JavaScript, anyone can read your source and modify or delete your Content Fragments. CF OpenAPI belongs behind a server-side proxy, not in browser code.

Common operations

List all fragments of a given model

GET /adobe/sites/cf/fragments
  ?modelId=/conf/ue-demo/settings/dam/cfm/models/hero
  &limit=20
  &offset=0

Authorization: Bearer {access_token}
X-Adobe-Accept-Unsupported-API: 1

Get a single fragment by its UUID

# Fragment UUIDs are visible in the CF editor URL or in list responses
GET /adobe/sites/cf/fragments/{fragment-uuid}

Authorization: Bearer {access_token}

Get a fragment by its DAM path

# Path-based lookup — useful when you know the DAM structure
GET /adobe/sites/cf/fragments
  ?path=/content/dam/ue-demo/fragments/offers-home-hero

Authorization: Bearer {access_token}

What the response looks like

{
  "id": "3f8a2c1d-...",
  "path": "/content/dam/ue-demo/fragments/offers-home-hero",
  "title": "Offers Home Hero",
  "model": { "id": "/conf/ue-demo/settings/dam/cfm/models/hero" },
  "fields": [
    { "name": "eyebrow",     "type": "text",      "values": ["Summer Sale"] },
    { "name": "title",       "type": "text",      "values": ["Up to 40% off PS Store"] },
    { "name": "description", "type": "richtext",  "values": ["<p>Score massive savings...</p>"] },
    { "name": "ctaLabel",    "type": "text",      "values": ["Shop the Sale"] }
  ]
}
Response shape differs from GraphQL

CF OpenAPI returns fields as a flat array of { name, type, values } objects, not the nested model-shaped object you get from GraphQL. You'll need a small adapter function to reshape it for your React components.

Adapter to normalize CF OpenAPI response to GraphQL shape

// Converts CF OpenAPI field array → the shape your components expect
function normalizeCFApiFragment(fragment) {
  const out = { _path: fragment.path };
  (fragment.fields || []).forEach(f => {
    out[f.name] = f.values?.length === 1 ? f.values[0] : f.values;
  });
  return out;
}

// Result has the same shape as a GraphQL response item:
// { _path, eyebrow, title, description, ctaLabel, image }

Node.js server-side example

// server/aem-cf.js — runs on your server, never in the browser
import { getAccessToken } from './ims-auth.js'; // your IMS token helper

const AEM_HOST = 'https://author-p138879-e1741192.adobeaemcloud.com';

export async function getFragment(path) {
  const token = await getAccessToken();
  const url = `${AEM_HOST}/adobe/sites/cf/fragments?path=${encodeURIComponent(path)}`;
  const res = await fetch(url, {
    headers: {
      Authorization: `Bearer ${token}`,
      'X-Adobe-Accept-Unsupported-API': '1',
    },
  });
  if (!res.ok) throw new Error(`CF API ${res.status}`);
  const data = await res.json();
  return normalizeCFApiFragment(data.items?.[0]);
}

3 — Author-only access: preview without publishing

A common scenario for internal tooling, staging previews, or content QA: you want to read draft CF content from Author before it's published, without standing up or waiting for Publish replication.

Option A: CF OpenAPI targeting Author

Point your CF OpenAPI calls at the Author hostname instead of Publish. Draft content is immediately readable — no replication step. Because this requires a token, it's only suitable for server-side code or authenticated internal tools.

# Reads draft content directly — no publish step needed
GET https://author-p138879-e1741192.adobeaemcloud.com/adobe/sites/cf/fragments?path=...
Authorization: Bearer {token}

Option B: GraphQL targeting Author

AEM's GraphQL endpoint exists on Author too, at the same path as Publish. With a valid session cookie or token, you can run persisted queries against Author to read unpublished drafts.

# Same query URL, different host
https://author-p138879-e1741192.adobeaemcloud.com
  /graphql/execute.json/global/heroByPath3
  ;path=/content/dam/ue-demo/fragments/offers-home-hero
  ;variation=master
CORS will block this from a public SPA — by design

Author is not configured to accept cross-origin requests from arbitrary frontend origins, and it shouldn't be. If you try to fetch from Author in a browser-based React app, CORS will block it and the app will fall back to placeholder data. This is not a bug to work around — it's the correct security boundary. Use CF OpenAPI from a server-side proxy instead.

Option C: Local Development Environment (local SDK)

If you're developing locally against the AEM SDK (not Cloud Service), your Author runs on localhost:4502 and Publish on localhost:4503. CORS is more permissive by default, and you can configure it freely. GraphQL persisted queries work on both. This is the one case where pointing your app at Author from a browser is practical — it's all local.

# Local SDK
Author:  http://localhost:4502
Publish: http://localhost:4503

# Query against local Author during development
http://localhost:4503/graphql/execute.json/global/heroByPath3;path=...

4 — What if there's no AEM instance at all?

Sometimes a demo environment has no live AEM instance, or the Publish endpoint is temporarily unavailable. Your React app should handle this gracefully.

The fallback data pattern (already in Part 1)

If every GraphQL fetch returns null or throws, the app renders from hardcoded fallback values. This is not a degraded state — for a demo, fallback data can be the intended content. Structure your fallbacks to match exactly what the live CF would return:

const FALLBACK_HERO = {
  eyebrow:     'Summer Sale',
  title:       'Up to 40% off PS Store',
  description: 'Score massive savings on PS5 games, add-ons, and subscriptions.',
  ctaLabel:    'Shop the Sale',
  image:       { _publishUrl: 'https://your-cdn.com/hero-bg.jpg' },
};

Static JSON file as a content proxy

If you want content to be editable without any AEM instance, export your CF data to a static JSON file co-deployed with your app. Your fetch function falls back to this file if the AEM endpoint is unreachable:

async function fetchHeroWithFallback(slug) {
  try {
    const data = await fetchHero(slug); // tries AEM Publish first
    if (data) return data;
  } catch {}

  // Fall back to static JSON bundled with the app
  const res = await fetch(`/content/${slug}.json`);
  return res.ok ? await res.json() : FALLBACK_HERO;
}

Adobe's headless trial / sandbox

Adobe provides a shared headless demo environment for evaluating AEM's content API without standing up your own instance. The GraphQL endpoint and sample content fragments are pre-provisioned. Useful for initial prototyping before a customer environment is available — check the AEM Headless Developer Portal for current sandbox credentials.

The architecture is the same regardless of the delivery method

Whether you're using GraphQL against Publish, CF OpenAPI against Author, or static JSON fallbacks — your React components don't change. Keep all the data-fetching logic in src/lib/aem.js and swap the implementation there. Components just receive props.
