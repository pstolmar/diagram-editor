React + AEM Content Fragments

A practical guide to building content-driven React SPAs on AEM Cloud Service

This guide covers everything you need to go from zero to a working React single-page application that reads live content from AEM Content Fragments. No framework magic, no hand-waving — just the actual endpoints, query syntax, code patterns, and infrastructure pieces that matter.

1 — How the pieces fit together

AEM Cloud Service gives you three distinct tiers, each with a specific job:

Author

Where content editors work. Every change — a headline edit, a new image, a CF variation — lives here first as a draft. Nothing on Author is visible to the public until it's published.

URL pattern: author-p{prog}-e{env}.adobeaemcloud.com

Publish

The public-facing content API. When an editor hits Publish in AEM or Universal Editor, content replicates here in seconds. Your React app always reads from Publish — never Author.

URL pattern: publish-p{prog}-e{env}.adobeaemcloud.com

CDN / Edge Delivery

Publish sits behind a global CDN. Responses are cached at the edge, so your GraphQL requests return in milliseconds worldwide. Cache is invalidated automatically on publish.

Cloud Manager

The deployment control plane — not a content system. You use it to provision environments, run CI/CD pipelines, and deploy OSGi config bundles (like CORS settings). Think of it as the ops layer above AEM.

Your React app only ever talks to the Publish tier. Author is for editors; Cloud Manager is for operators.

2 — Cloud Manager: what you actually need to know

Cloud Manager (experience.adobe.com → Cloud Manager) organizes everything into Programs and Environments.

Programs and environments

A Program maps to a project or product line. Each Program contains one or more Environments. Each environment has a numeric ID baked into its hostname:

# This demo's identifiers
Program:     p138879
Environment: e1741192

Author:   https://author-p138879-e1741192.adobeaemcloud.com
Publish:  https://publish-p138879-e1741192.adobeaemcloud.com

Environment types

TypeWhat it's forNotes
ProductionLive trafficDeployed via full pipeline only; no shortcuts
StagePre-production QASame pipeline as Prod; mirrors Prod config
DevFeature developmentCan deploy individual packages
RDERapid Development Environment — inner-loop testingDeploy in seconds without a pipeline; use aio aem:rde:install

Deploying config changes (e.g., CORS)

AEM server-side configuration lives in OSGi config bundles deployed as content packages. To update CORS settings so your Publish instance allows cross-origin requests from your SPA's domain:

# Install via Adobe I/O CLI to the RDE
aio aem:rde:install your-config.ui.config-1.0.zip -t content-package

# For Stage/Prod: commit the config to your Cloud Manager git repo,
# then trigger a pipeline deploy through the Cloud Manager UI.
CORS is the first thing that will break you

Browsers block cross-origin requests unless the server explicitly allows your origin. Your Publish instance must return Access-Control-Allow-Origin: https://your-site.com for every GraphQL response. Set this up before writing a single line of React.

Pipelines

A pipeline connects your git repo to an AEM environment. The full-stack pipeline builds your project (Maven), runs tests, and deploys code + content. For most SPA setups, the only pipeline work you need is deploying OSGi configs (CORS, GraphQL settings). Your React app itself deploys independently — AEM doesn't build or host it.

3 — Content Fragments: structured content for developers

A Content Fragment (CF) is a structured piece of content defined by a model — essentially a schema. The model defines fields (text, rich text, references, numbers), and editors fill in values for each fragment instance. Fragments live in the DAM at /content/dam/….

Variations

Every CF has a master variation (the default) plus any number of named variations an editor creates. This is how you get AI-generated copy variants, locale-specific content, or audience-targeted messaging — all stored in one fragment, accessed with a simple parameter change at query time.

# Same fragment, three different variations
/content/dam/ue-demo/fragments/ps-ghost/jcr:content/data/master
/content/dam/ue-demo/fragments/ps-ghost/jcr:content/data/punchy
/content/dam/ue-demo/fragments/ps-ghost/jcr:content/data/seo

Content Fragment Models

Before you can create fragments, an admin defines the model in AEM's Tools → Assets → Content Fragment Models. The field names in that model are what you reference everywhere — in GraphQL queries, in Universal Editor instrumentation attributes, and in your React rendering code. Keep them consistent.

Fields used in this demo's hero model:

Field nameTypePurpose
eyebrowSingle-line textSmall label above the headline ("Summer Sale")
titleSingle-line textMain headline
descriptionRich textBody copy — returns HTML string from GraphQL
ctaLabelSingle-line textButton label ("Shop the Sale")
imageContent referenceDAM asset; GraphQL returns _publishUrl

4 — GraphQL: reading content from your React app

AEM exposes Content Fragments via a GraphQL API. Rather than ad-hoc queries, AEM uses persisted queries — queries saved on the server and executed by URL. This keeps your frontend code simple and lets AEM cache responses at the CDN level.

The endpoint pattern

https://publish-p{prog}-e{env}.adobeaemcloud.com
  /graphql/execute.json
  /{project-name}
  /{query-name}
  ;{param1}={value1}
  ;{param2}={value2}

Parameters are semicolon-separated path segments, not query string params. This is deliberate — it makes the full URL cacheable by CDN (query strings often bypass caches).

The queries used in this demo

Fetch a single fragment by path (master variation)

// Fetch the hero CF at its DAM path
const path = '/content/dam/ue-demo/fragments/offers-home-hero';

fetch(
  `https://publish-p138879-e1741192.adobeaemcloud.com`
  + `/graphql/execute.json/global/heroByPath3`
  + ';path=' + path
  + ';variation=master'
  + ';_t=' + Date.now(),        // cache-bust during development
  { headers: { Accept: 'application/json' }, cache: 'no-store' }
)
.then(r => r.json())
.then(d => d?.data?.homeHeroByPath?.item ?? null);

Fetch a specific CF variation

// The only change: swap the variation parameter
const fetchVariation = (slug, variation) => {
  const path = `/content/dam/ue-demo/fragments/` + slug;
  return fetch(
    `https://publish-p138879-e1741192.adobeaemcloud.com`
    + `/graphql/execute.json/global/heroByPath3`
    + ';path='      + path
    + ';variation=' + (variation || 'master')
    + ';_t='        + Date.now(),
    { headers: { Accept: 'application/json' }, cache: 'no-store' }
  )
  .then(r => r.json())
  .then(d => d?.data?.homeHeroByPath?.item ?? null)
  .catch(() => null);
};

// Fetch all three variants in parallel
const [master, punchy, seo] = await Promise.all([
  fetchVariation('ps-ghost', 'master'),
  fetchVariation('ps-ghost', 'punchy'),
  fetchVariation('ps-ghost', 'seo'),
]);

What the response looks like

Rich text fields

Rich text returns an object with an html property, not a plain string. Render it with dangerouslySetInnerHTML in React — or use a sanitizer like DOMPurify if the content comes from untrusted sources.

Remove cache-busting in production

The ;_t=Date.now()

suffix forces a fresh response on every load — useful during development when you're iterating on CF content, but it defeats CDN caching in production. Remove it before going live.

Creating and managing persisted queries

Persisted queries are created and managed in AEM's GraphiQL Explorer (Author → Tools → GraphQL). Each query is saved under a project namespace (e.g., global) and given a name. The query definition lives in AEM — you only call it by URL from your frontend. To modify a query, update it in GraphiQL and republish it; no frontend deploy required.

5 — Setting up your React app

AEM doesn't build, host, or care about your React app. It's a static site or SPA deployed wherever you want — Adobe Edge Delivery Services, Vercel, S3, wherever. AEM is purely the content API.

Recommended project structure

my-app/
├── index.html          ← entry point
├── src/
│   ├── main.jsx        ← ReactDOM.createRoot(...)
│   ├── App.jsx
│   ├── components/
│   └── lib/
│       └── aem.js      ← all AEM fetch functions in one place
└── vite.config.js

Isolate all AEM calls in one file

Keep every GraphQL fetch in a single module. This makes it easy to swap the endpoint for different environments and easy to mock in tests.

// src/lib/aem.js
const PUBLISH = 'https://publish-p138879-e1741192.adobeaemcloud.com';
const OPTS    = { headers: { Accept: 'application/json' } };

const gql = (query, params = {}) => {
  const seg = Object.entries(params).map(([k,v]) => `;${k}=${v}`).join('');
  return fetch(`${PUBLISH}/graphql/execute.json/global/${query}${seg}`, OPTS)
    .then(r => { if (!r.ok) throw new Error(r.status); return r.json(); });
};

export const fetchHero = (slug, variation = 'master') =>
  gql('heroByPath3', {
    path: `/content/dam/ue-demo/fragments/` + slug,
    variation,
  })
  .then(d => d?.data?.homeHeroByPath?.item ?? null)
  .catch(() => null);

export const fetchAllVariations = (slug) =>
  Promise.all(['master', 'punchy', 'seo'].map(v => fetchHero(slug, v)));

Always define fallback data

GraphQL fetches can fail — network error, CDN cold start, unpublished content. Define hardcoded fallback values so your page always renders something meaningful instead of crashing or showing empty fields.

// Shown if the CF fetch fails or returns nothing
const FALLBACK_HERO = {
  eyebrow:     'Summer Sale',
  title:       'Save Up to 40% on PS Store',
  description: 'Score massive savings on PS5 games and subscriptions.',
  ctaLabel:    'Shop the Sale',
};

function Hero({ data = FALLBACK_HERO }) {
  return (
    <section>
      <p>{data.eyebrow}</p>
      <h1>{data.title}</h1>
      <button>{data.ctaLabel}</button>
    </section>
  );
}

Loading pattern in your top-level component

import { useState, useEffect } from 'react';
import { fetchHero, fetchAllVariations } from './lib/aem.js';

export default function App() {
  const [hero,     setHero]     = useState(FALLBACK_HERO);
  const [variants, setVariants] = useState(FALLBACK_VARIANTS);

  useEffect(() => {
    fetchHero('offers-home-hero')
      .then(d => { if (d) setHero(d); });

    fetchAllVariations('ps-ghost')
      .then(([master, punchy, seo]) => {
        setVariants({ master: master ?? FALLBACK_VARIANTS.master,
                      punchy: punchy ?? FALLBACK_VARIANTS.punchy,
                      seo:    seo    ?? FALLBACK_VARIANTS.seo });
      });
  }, []);

  return <Hero data={hero} />;
}
Start with the fallback, render immediately

Initialize state with the fallback data so the page renders on first paint, before the fetch resolves. This avoids a blank screen and is especially important for the Universal Editor, which needs to see DOM nodes immediately to populate the Content Tree.

6 — Simulating a future date for demo purposes

If your page has time-sensitive content (countdown timers, sale windows, content that changes on a specific date), you can add a ?date=YYYYMMDD parameter to preview it as it will appear on any future date — without freezing the clock.

// Capture the real wall-clock time at page load
const SIM_REAL_START = Date.now();

// Parse ?date=20260801 from the URL
const SIM_DATE = (() => {
  const m = location.search.match(/[?&]date=(\d{8})/);
  if (!m) return null;
  const s = m[1];
  return new Date(`${s.slice(0,4)}-${s.slice(4,6)}-${s.slice(6,8)}T00:00:00Z`);
})();

// In any countdown or date-relative logic:
// Offset the simulated start by however much real time has elapsed
const now = SIM_DATE
  ? SIM_DATE.getTime() + (Date.now() - SIM_REAL_START)
  : Date.now();

Opening newoffers.html?date=20260801 simulates the page as of midnight UTC August 1, 2026, with every countdown ticking forward in real time from that point.

7 — Before you write your first component

  1. 1 Confirm your AEM environment IDs (p… and e…) from Cloud Manager
  2. 2 Verify your Content Fragment models exist in Author → Tools → Assets → Content Fragment Models
  3. 3 Confirm at least one CF is published (not just saved on Author) and visible via a direct GraphQL fetch to Publish
  4. 4 Deploy CORS config to your AEM environment allowing your app's origin (https://your-site.com)
  5. 5 Test the raw GraphQL URL in your browser before touching React — if it doesn't work there, it won't work in your app
  6. 6 Define fallback data before writing any fetch code — initialize React state with it on mount
  7. 7 Keep all AEM fetch functions in one isolated module (src/lib/aem.js)
