Migration is not a big bang

It's a series of small wins.

Each step delivers value independently. Teams can tackle different steps in parallel. Nothing requires a cutover day.

1
Audit
List all XFs, Core Components, custom components. Map them to EDS equivalents. Identify which have backend data dependencies.
2
Start with the footer
Lowest dependency, immediate CDN caching win. One JS + CSS file replaces a 23-component XF.
3
Migrate static XFs
Nav, promo banners, page headers. No backend data. Word table → block in an afternoon.
4
Tackle data-driven components
Replace Java OSGi services with serverless Workers. Block calls Worker, Worker calls the real API.
5
Move Content Fragments
Already headless. Switch from Sling include to GraphQL fetch. Add data-aue-* for UE.
6
Retire AEM publish
Once delivery is edge-cached blocks, the AEM publish tier is no longer on the critical path — only used for authoring.

The real customer concern

Custom Java Components with Backend Data

"Our most important component calls our internal pricing/inventory/personalization API from Java. How do we migrate that?"

history How it worked in AEM 
AEM Author
  └─ Sling Model (@Model)
      └─ OSGi Service
          └─ HTTP call → api.company.com/v2/price
              └─ JCR cache (5 min TTL)
  → HTL renders price at publish time
  → Page cached in Dispatcher
  → Price is stale (publish + dispatcher)
Price shown is often 2–3 Dispatcher TTL periods stale. Flush = AEM publish + Dispatcher flush = IT ticket.
bolt How it works in EDS 
Browser (block decorate() fn)
  └─ fetch('/api/worker/price')
      └─ Cloudflare Worker (or AWS Lambda)
          └─ HTTP call → api.company.com/v2/price
              └─ Edge cache (30s TTL, automatic)
  → Price updates every 30s in browser
  → No AEM in the delivery path
  → Flush = Worker re-deploy (< 30s globally)
Same API, fresher data, zero AEM infrastructure in the critical path.
lightbulb
The migration question to ask for every custom component

When you have a custom AEM component with a backend dependency, the migration question is: What Worker will replace this service call? The block code is trivial — the interesting part is the Worker. The Java OSGi service becomes a serverless function. The Dispatcher cache becomes edge cache. The IT ticket becomes a 30-second deploy.
