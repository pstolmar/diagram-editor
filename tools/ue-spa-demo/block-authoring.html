1 — Block Anatomy: The Contract

A block is a folder with two files. That's it.

blocks/
  └── teaser/
      ├── teaser.js   ← decorator function (required)
      └── teaser.css  ← styles (optional but conventional)

AEM EDS auto-discovers blocks by matching the CSS class on a <div> element to a folder under blocks/. When a match is found, EDS dynamically imports blocks/teaser/teaser.js and calls decorate(block).

The decorate(block) contract

// blocks/teaser/teaser.js
// AEM EDS calls this once per .teaser element on the page.
// block = the DOM element matching the block name.
export default function decorate(block) {
  // block.children = rows from the Word/Google Doc table
  // Each row  = one <div>
  // Each cell = nested <div>
  // Your job: transform this raw structure into semantic HTML.

  const [[imageCell], [textCell]] = [...block.children].map(
    row => [...row.children]
  );
  // Now restructure, add classes, fetch data, wire events...
}

Word table → HTML mapping

When an author creates a table in their document, EDS converts it to nested <div> elements before your decorator runs:

Word table
┌─────────────────┐
│  /image.jpg     │
│                 │
├─────────────────┤
│  Title          │
│  Description    │
│  [CTA button]   │
└─────────────────┘
→
Delivered HTML
<div class="teaser">
  <div>           ← row 1
    <div>image</div>  ← cell 1
  </div>
  <div>           ← row 2
    <div>Title</div>
    <div>Desc</div>
    <div>CTA</div>
  </div>
</div>
Key rule Block name === folder name === CSS class

A block named my-teaser must live at blocks/my-teaser/my-teaser.js. The folder, the JS file, and the CSS class on the page element must all match exactly — the comparison is case-sensitive. One character off and the block silently does not load.

2 — Step-by-Step: Build a Teaser Block from Scratch

1
Create the files
mkdir -p blocks/teaser
touch blocks/teaser/teaser.js blocks/teaser/teaser.css
2
Write the decorator

Read the rows, pull content from the cells, clear the block, and rebuild with semantic HTML:

// blocks/teaser/teaser.js
export default function decorate(block) {
  const rows = [...block.children];
  const hasMedia = rows.length > 1;
  const [mediaRow, contentRow] = hasMedia ? rows : [null, rows[0]];

  const img = mediaRow?.querySelector('img');
  const [eyebrowEl, titleEl, descEl, ctaEl] = [...(contentRow?.children ?? [])];

  block.innerHTML = '';

  if (img) {
    const media = document.createElement('div');
    media.className = 'teaser-media';
    media.append(img);
    block.append(media);
  }

  const body = document.createElement('div');
  body.className = 'teaser-body';

  if (eyebrowEl) {
    const e = document.createElement('p');
    e.className = 'teaser-eyebrow';
    e.textContent = eyebrowEl.textContent;
    body.append(e);
  }
  if (titleEl) {
    const h = document.createElement('h2');
    h.textContent = titleEl.textContent;
    body.append(h);
  }
  if (descEl) body.append(descEl);
  if (ctaEl) {
    ctaEl.className = 'teaser-cta';
    body.append(ctaEl);
  }
  block.append(body);
}
3
Write the CSS
/* blocks/teaser/teaser.css */
.teaser {
  display: grid;
  grid-template-columns: 1fr 1fr;
  gap: 2rem;
  align-items: center;
}

.teaser-media img {
  width: 100%;
  height: auto;
  border-radius: 6px;
  display: block;
}

.teaser-eyebrow {
  font-size: 0.8rem;
  text-transform: uppercase;
  letter-spacing: 0.1em;
  color: var(--color-brand, #1473e6);
  margin-bottom: 0.5rem;
}

.teaser-body h2 { font-size: 1.5rem; margin-bottom: 0.75rem; }

.teaser-cta a {
  display: inline-block;
  padding: 0.6rem 1.4rem;
  background: var(--color-brand, #1473e6);
  color: #fff;
  text-decoration: none;
  border-radius: 4px;
}

@media (max-width: 600px) {
  .teaser { grid-template-columns: 1fr; }
}
4
Author it in a Word doc or Google Doc

Create a table anywhere in your document. The first row holds the image, the second row holds the text content — one cell per content field:

┌─────────────────────────────────────────┐
│  Teaser                                 │  ← header row sets the block name
├─────────────────────────────────────────┤
│  /content/dam/mysite/hero.jpg           │  ← row 1, cell 1: image
├──────────────┬──────────────────────────┤
│  New Feature │                          │  ← row 2, cell 1: eyebrow
├──────────────┴──────────────────────────┤
│  The headline goes here                 │  ← row 2, cell 2: title
├─────────────────────────────────────────┤
│  A short supporting description.        │  ← row 2, cell 3: description
├─────────────────────────────────────────┤
│  Learn more  →  /products/feature       │  ← row 2, cell 4: CTA
└─────────────────────────────────────────┘
Tip Block name variants

You can pass variants by adding them to the header row: Teaser (dark, compact). EDS adds dark and compact as additional CSS classes on the block element. Your decorator can branch on block.classList.contains('dark').

5
Test with aem up
aem up
# Starts local dev proxy at http://localhost:3000
# Visit http://localhost:3000/your-page
# EDS fetches your document, converts it to HTML,
# then calls decorate() on the .teaser element.

Open DevTools and inspect the rendered block. Confirm the .teaser-media and .teaser-body divs are present. If the block wrapper is there but looks wrong, your decorator is running — check the cell extraction logic.

3 — Universal Editor Instrumentation

Two things are needed in <head> before Universal Editor can see the page at all:

<!-- Declare which AEM Author instance owns this page -->
<meta name="urn:adobe:aue:system:aem"
      content="aem:https://author-p138879-e1741192.adobeaemcloud.com"/>

<!-- Load the UE client bridge that handles postMessages and auth -->
<script src="https://universal-editor-service.adobe.io/cors.js" async></script>

Once the page loads inside the UE iframe, you also need data-aue-* attributes on your DOM elements to declare what is editable. Choose one of two approaches:

Approach A — Component model (for EDS page-specific content)

Register the block's editable fields in component-models.json at the site root. EDS reads this file when resolving the block's Properties panel in UE.

// component-models.json (merged from models/ by npm run build:json)
{
  "id": "teaser",
  "fields": [
    { "component": "text",       "name": "eyebrow",     "label": "Eyebrow",      "valueType": "string" },
    { "component": "text",       "name": "title",      "label": "Title",       "valueType": "string" },
    { "component": "richtext",  "name": "description", "label": "Description" },
    { "component": "aem-content", "name": "image",  "label": "Image" }
  ]
}

Then, at the end of your decorate() function (after rebuilding the DOM), add the UE attributes to the block container:

// At the END of decorate() — after all DOM mutations
const pageRes = document.querySelector('[name="aue-resource"]')?.content ?? '';
block.dataset.aueResource = `urn:aem:${pageRes}`;
block.dataset.aueType     = 'component';
block.dataset.aueModel    = 'teaser';    // must match component-models.json "id"
block.dataset.aueLabel    = 'Teaser';

Approach B — Content Fragment-backed (for reusable/shared content)

When the same content appears across multiple pages, store it in a Content Fragment and point each block instance at the CF path. Do not use a component model — UE derives the field list from the CF model directly.

// blocks/teaser/teaser.js — CF-backed variant
const FRAG  = '/content/dam/mysite/fragments/teaser-home/jcr:content/data/master';
const RES   = 'urn:aem:' + FRAG;

// After building the DOM in decorate(), annotate each field element:

eyebrowEl.dataset.aueResource = RES;
eyebrowEl.dataset.aueProp     = 'eyebrow';
eyebrowEl.dataset.aueType     = 'text';
eyebrowEl.dataset.aueLabel    = 'Eyebrow';

titleEl.dataset.aueResource   = RES;
titleEl.dataset.aueProp       = 'title';
titleEl.dataset.aueType       = 'text';
titleEl.dataset.aueLabel      = 'Title';

descEl.dataset.aueResource    = RES;
descEl.dataset.aueProp        = 'description';
descEl.dataset.aueType        = 'richtext';
descEl.dataset.aueLabel       = 'Description';

// Container: resource + type only. NO data-aue-model.
block.dataset.aueResource     = RES;
block.dataset.aueType         = 'component';
block.dataset.aueLabel        = 'Teaser';
Critical Never add data-aue-model to a CF-backed block container

When data-aue-model is present, UE calls the /details API endpoint to look up the component model definition in your component-models.json. When no matching model ID is found — which is always the case for CF-backed blocks — UE returns HTTP 500 and the Properties panel breaks entirely. For CF-backed editing, omit data-aue-model from the container. UE reads the field structure from the CF model directly.

UE attribute quick reference

Attribute Where to put it Value
data-aue-resource Container + every field element urn:aem:/content/dam/.../jcr:content/data/master
data-aue-type Container element component
data-aue-type Plain text field text
data-aue-type Rich text / HTML field richtext
data-aue-type Image field image
data-aue-prop Every field element CF field name, e.g. eyebrow, title, ctaLabel
data-aue-label Every field element Human-readable label shown in UE Properties panel
data-aue-model Container (Approach A only) Must match "id" in component-models.json. Omit for CF-backed approach.

4 — Converting a Core Component to an EDS Block

The full recipe for migrating an AEM Core Component (Teaser, Hero, Cards, etc.) to an EDS block.

1
Audit the Core Component dialog fields

Open the Core Component dialog in CRXDE at /apps/core/wcm/components/teaser/v2/teaser/cq:dialog. List every field the author can fill in. For the Teaser v2, the typical fields are:

  • pretitle — eyebrow / pre-title text
  • jcr:title — headline
  • titleType — heading level (H1–H6)
  • jcr:description — body copy
  • fileReference — image DAM path
  • titleLink — link on the headline
  • actions — array of CTA links
  • hideDescription, hideTitle — display toggles
2
Decide: block rows or Content Fragment
Use block rows (Word table) Use a Content Fragment
Content is unique to this page Content appears on 2+ pages
Author owns it in the document Content team owns it centrally in DAM
Simple text + image, no variants Multiple language variants / personalisation targets
Teaser: usually page-specific Hero, global promo banner: usually CF
3
Export existing content from the JCR

Use Query Builder to find all existing Teaser instances so you know what data to migrate:

GET /bin/querybuilder.json
    ?type=nt:unstructured
    &property=sling:resourceType
    &property.value=core/wcm/components/teaser/v2/teaser
    &p.limit=-1
    &p.hits=full

Map the JCR properties to your block's row structure:

JCR property Block row / CF field
pretitle Row 2, cell 1 (eyebrow)
jcr:title Row 2, cell 2 (title)
jcr:description Row 2, cell 3 (description)
fileReference Row 1, cell 1 (image path)
actions/item0/jcr:title + link Row 2, cell 4 (CTA: text + URL)
4
Create the Word docs / DA pages

For each migrated page, open the DA (Document Authoring) page and recreate the Teaser as a table. One row per content group, one cell per field, matching the structure your new block's decorate() expects. Use the image DAM path directly in a cell — EDS resolves it to an <img> tag automatically.

5
Remove the Core Component instances

Once you have verified each migrated page renders correctly in aem up and on the preview URL, delete the Core Component nodes from the JCR page structure. In CRXDE, locate the jcr:content/root/container/teaser_XXXXX node and delete it. Activate the page to push the deletion to Publish.

6
Remove the OSGi / Maven dependency (if applicable)

If your project included the Core Components all-in-one package, remove it once no Core Component types remain in use:

<!-- pom.xml — remove this dependency block -->
<dependency>
  <groupId>com.adobe.cq</groupId>
  <artifactId>core.wcm.components.all</artifactId>
  <version>2.x.x</version>
  <type>zip</type>
</dependency>
Caution Remove incrementally

Remove the Core Component dependency only after all instances of every Core Component type have been migrated. Removing it while any page still references core/wcm/components/... causes a 500 on those pages in AEM Author.

5 — Common Pitfalls

Each block below is one failure pattern. Red = what you see. Yellow = why it happens. Green = exact fix.

If you see this behavior

The block container div is present in the DOM but nothing inside it renders. No JS errors in the console.

It means

The JS file name doesn't match the CSS class name on the block element. EDS constructs the import path from the class name and uses an exact string match — case-sensitive. A block with class my-Block looks for blocks/my-Block/my-Block.js, which doesn't exist if you named the folder my-block.

Fix it this way

Use all-lowercase, hyphenated names for everything: folder name, JS file name, CSS file name, and the class used in the document. The rule is: folder = file stem = CSS class, all lowercase with hyphens. No camelCase, no underscores.

# Correct
blocks/my-teaser/my-teaser.js   → class="my-teaser" on the page element

# Incorrect — will silently fail
blocks/myTeaser/myTeaser.js     → class="my-teaser" ← mismatch
If you see this behavior

decorate() is never called. The block HTML remains as raw nested divs. The browser console shows no import errors.

It means

A JS syntax error in your file prevents the module from loading. The dynamic import() in scripts/aem.js rejects silently when the module fails to parse. Common causes: missing semicolons, a stray const before the export default, or a template literal that isn't closed.

Fix it this way

Open the Network tab, filter for your block JS file, and check its status. If it's 200 but still not running, open the Sources tab, navigate to the file, and look for a parse error marker. Alternatively, run the linter:

npm run lint:js blocks/teaser/teaser.js

Also confirm the function is the default export: export default function decorate(block) { ... }

If you see this behavior

You click the block inside Universal Editor but no fields appear in the Properties panel (right sidebar). The Content Tree shows the component.

It means

data-aue-prop attributes were placed on the original cell elements, but your decorate() function clears the block with block.innerHTML = '' before annotating — so the annotated elements are discarded and replaced with unannotated ones. UE reads the DOM after decoration completes; it never sees the original cells.

Fix it this way

Add all data-aue-* attributes after you have finished rebuilding the DOM — on the new elements you created, not on the original cells. A reliable pattern is to set them at the very end of decorate():

export default function decorate(block) {
  // 1. Destructure original cells
  // 2. Clear block and rebuild DOM
  // 3. Append all new elements

  // 4. Only NOW add UE attributes:
  const RES = 'urn:aem:/content/dam/.../jcr:content/data/master';
  titleEl.dataset.aueResource = RES;
  titleEl.dataset.aueProp     = 'title';
  titleEl.dataset.aueType     = 'text';
  titleEl.dataset.aueLabel    = 'Title';
}
If you see this
Failed to fetch details
URL: https://universal-editor-service.adobe.io/details
Backend responded with: 500
It means

data-aue-model is present on a container element. UE calls /details to look up the component model definition from your site's component-models.json. When the model ID isn't registered there — or the file isn't served from the site root — the lookup returns 500 and the Properties panel breaks for that component.

Fix it this way

CF-backed approach: Remove data-aue-model from the container entirely. UE reads the editable field structure from the Content Fragment model automatically.

Component model approach: Ensure the model ID in data-aue-model exactly matches an "id" entry in component-models.json, and that the file is served at the site root. Run npm run build:json to regenerate the merged file from the models/ fragments.

If you see this behavior

Block renders correctly on localhost:3000 but fails to load on *.aem.live or *.aem.page. Browser console shows a module import error.

It means

An import path in your block JS is missing the .js extension. Node.js and bundlers resolve bare imports like import { foo } from './utils' without extensions, but EDS uses native ES module import() in the browser, which requires explicit extensions. The ESLint airbnb-base config enforces this locally — a missing extension is a lint error — but the error is only surfaced when the linter runs, not by the local dev proxy.

Fix it this way

Always include the .js extension on all import paths. Run the linter before pushing:

# Correct
import { formatDate } from './utils.js';
import { loadCSS } from '../../scripts/aem.js';

# Incorrect — works on localhost, breaks in the browser
import { formatDate } from './utils';
npm run lint:js   # catches missing extensions before you push
