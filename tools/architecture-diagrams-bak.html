1

System Architecture

Four-layer stack. Players hit a globally-cached EDS CDN page, which calls a stateless I/O Runtime action, which reads and writes a Redis-backed KV store. No auth needed for players.

2

Game Session Lifecycle

Phase state machine, all 8 teams, and the 4 vote tiers (point values hidden by default — click 👁 to reveal).

Vote Submission — CAS Write Flow

How a single player's vote travels from browser click to confirmed Redis write. The CAS verify step is what prevents silent lost updates under burst load.

4

Claude Code Deploy Flow & Frontend Performance

How this system was built and deployed — Claude Code CLI with Adobe's FluffyJaws MCP, two separate deployment targets, and why the frontend is fast.

Load Test Results

Four progressive test runs showing the impact of CAS (compare-and-swap) and realistic player pacing on vote integrity and latency. Final result: 200/200 votes, 0 drops.

%%  AI Club Robot Game — Full Vote Flow

sequenceDiagram
    actor P as 🎮 Player (up to 200)
    participant EDS as AEM Edge Delivery
    participant RT  as Adobe I/O Runtime — robot-game
    participant KV  as aio-lib-state (Redis KV)

    P->>EDS: GET /tools/ai-club-pit-crew-challenge.html
    EDS-->>P: Static HTML + JS (CDN cached — zero server cost)

    P->>RT: GET ?mode=join
    RT-->>P: { teamSlug: "token-titans", teamName: "Token Titans" }

    Note over P: Player selects mobility / utility / care / brain options

    P->>RT: POST ?mode=submit { teamSlug, build: { mobility, utility, care, brain } }

    loop withRetry — up to 6 attempts · delays: 25, 25, 25, 25, 50, 50 ms
        RT->>KV: GET game-votes-token-titans
        KV-->>RT: { playerCount: N, mobility:{…}, _v: prevId }
        RT->>RT: increment playerCount · increment tier counts · set _v = writeId
        RT->>KV: PUT { playerCount: N+1, …, _v: writeId }
        RT->>KV: GET game-votes-token-titans  (CAS verify)
        alt verify._v === writeId
            Note over RT: ✅ Write confirmed — no concurrent writer overwrote us
        else verify._v !== writeId (another writer won the race)
            Note over RT: ⚡ CAS conflict — retry reads fresh state from winner
        end
    end

    RT->>KV: countTeamsReady() — parallel GET all 8 game-votes-* keys
    KV-->>RT: N records with playerCount > 0
    RT-->>P: { ok: true, teamsReady: N }  ·  200 OK

    Note over P,KV: ── Game ends when timer expires (300s) OR all 8 teams have ≥1 vote ──
    Note over P,KV: ── Timer is server-authoritative (expiresAt in Redis) — clients read via mode=status ──

    P->>RT: GET ?mode=status
    RT->>KV: GET game-session + parallel GET all 8 game-votes-* keys
    KV-->>RT: All vote records
    RT->>RT: computeActualBuild() — majority vote per tier · ties broken by point value
    RT->>KV: PUT game-session { phase: "results" }
    RT-->>P: { phase: "results", results: { 8 teams with actualBuild + score } }
